## Changes and self-review

Public ceremony starts retain the browser binding and additionally account for the trusted native request client key. Eight recent ceremonies from the same client exhaust its admission quota even when each request discards the binding cookie. The native adapter derives this key from Fastify's configured trusted proxy interpretation; request bodies cannot supply it. The persisted quota value is a digest. Internal callers without HTTP request context retain the existing browser and global bounds. A busy NAT can therefore reach the shared client quota; this is an intentional cost bound for anonymous authentication work.

PGP login, PGP enrollment and passkey enrollment now delegate the final state decision to pure domain transitions with explicit Malli input contracts. Crypto stays in the native adapter. The operation lock captures the reserved challenge record and its authenticated private bytes together. Completion may advance the mutable attempt counter, but cannot change the purpose, browser digest, private reference or absolute challenge interval. Enrollment captures the original session before verification, then rechecks that exact record, active actor and challenge ownership in the transaction. PGP login rechecks the exact credential that supplied the verified public key and refuses session collisions. Current transaction time is supplied as an explicit host fact. Existing sessions without an issuance timestamp remain accepted when the whole captured record is unchanged.

Readiness now awaits the existing bounded native contention retry before returning an unhealthy response. Persistent contention, missing ciphertext and invalid current references still fail closed. The response exposes no storage paths or secret data.

Private preparation has a scoped cleanup boundary. A failed signup or PGP enrollment considers only the blob prepared for that operation. ATProto SDK replacement/deletion returns the superseded reference from the durable transaction and considers only that reference for reclamation. Before deletion, cleanup takes the operation lock, replays current references, and fences the current identity ledger. A candidate referenced by a visible committed write remains intact even when the caller received a lost acknowledgment. SDK reads hold the same lock through reference lookup and unsealing, so replacement cleanup cannot delete their selected blob mid-read. Native deletion accepts only a regular main-vault file with a valid digest name and fences its containing directory.

Cleanup has a separate finite retry budget. Failure to prove that deletion is safe leaves the blob in place and reports a sanitized diagnostic; it never replaces a committed result or the original admission error. This change does not promise collection after a process crash, indefinite storage failure, or failure before the cleanup continuation runs. It deliberately avoids a blanket main-vault sweep that could delete another operation's prepared material. A future durable cleanup queue could cover that remaining crash window.
